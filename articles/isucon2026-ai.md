# AI 時代の ISUCON2026：優勝はハーネス、私たちはガードレール

ISUCON2026 は、優勝した Typing Bears が **3か月かけて作ったハーネスで AI エージェントに全部を任せ、競技中に人が一度も入力しないまま優勝した**ことで話題になりました。

私たち「パートナーズ」も、本番と感想戦で Claude Code を使いました。ただし力を入れたのは、AI を速くすることより、**ルール違反で失格にならないためのガード**でした。この記事では、両者の違いと、大会で AI を使うことについて考えたことをまとめます。

競技の内容と点数の推移は、[参加記](isucon2026-partners.md)にまとめています。

## 大会も AI の利用を前提にしていた

ISUCON2026 では、初期化の応答で、使ったエージェント、ハーネス、モデルを申告する決まりがありました（手作業なら `human`、`manual`、`brain`）。点数には使わず、調査と集計のためです。大会の側も、AI を使う参加者が多いことを前提にしていました。

## 優勝チーム：3か月かけたハーネス

優勝した Typing Bears は1人のチームで、Claude Code と Opus 5.5 を使っていました。当日の動きは[当日編](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)に、3か月の準備は[準備編](https://zenn.dev/luvtechno/articles/isucon2026-preparation)にまとめられています。

### 当日：人の入力は0回

- **競技中に人が入力した回数は0回。** 負荷走行86回とコミット19回を、すべてエージェントが実行しました。異常があれば Slack に通知しますが、返事は待たない作りでした。
- **構成は、メインのセッション1つと、監査役のサブエージェント1つ。** 点数が頭打ちになったときや、前回から60分たったときに監査役を起動させ、判断を見直させます。終了前の片付けと確認も、時刻を合図に指示していました。
- **11時台に約50万点。** DB をやめてメモリに持つ、署名を事前計算する、といった構成の変更を、競技の最初の1時間で済ませています。

### 準備：評価の仕組みを作り、159回解かせた

- **きっかけは、土曜日をいつもどおり過ごしながら参加したかったこと。** 全部を AI に任せられるかを確かめる準備でした。
- **期間と量。** 8/3〜10/30 の約3か月で、Issue 927、PR 754、コミット 3,889、評価の走行 159回（延べ674時間）。使ったトークンは約200億です。8時間の走行は、AWS の費用だけで1回約1,000円かかったそうです。
- **評価の仕組みを先に作った。** 環境を作り、エージェントを起動し、終了まで見張り、記録を回収して環境を消すまでを自動にしています。問題は、過去問5つ（ISUCON8・10・12・13・14）、非公式の ISUNARABE 2026、自作の予想問題の7問でした。
- **作り込んだ構成より、素に近い構成が強かった。** 作り込んだ構成（full）を育てていましたが、9/22 に素の Claude Code に近い構成（bare）が上回り、10/5 に full の開発を止めています。当日は、bare に最小限を足した構成（lite）でした。足したのは、起動時の指示（55行）、Stop フック、監査役、時刻を合図にした指示です。
- **規則の読み方を教えた。** 「文面が禁じていない手は、測って決める」こと、運営に確認できないことを理由に見送らないことを、指示に加えていました。
- **人が回したのは、準備の改善ループ。** 何で評価するか、どの改善を取り込むかは人が決めていて、準備の改善は最後まで人が入るループだったそうです。コミットの76%は Claude Code でした。
- **反省は、評価の土台の正しさ。** 評価環境の不具合（ファイル記述子の上限など）で構成の良し悪しを見誤ったこと、同じ構成でも走行ごとに点数が大きく揺れること、手順を細かく決めすぎると探索が狭まることを挙げていました。

感想戦で1位だった「急須で入れたような何か」も、人を介さないハーネスで約5時間で 575,333 点に届いています（[記事](https://zenn.dev/marie673/articles/isucon2026-full-harness)）。ハーネスについて、「点数の目安を渡すと守りに入るので外した」「区切りごとの報告と返事待ちが止まる原因になったので、記録だけにした」と書かれていました。

## 私たち：ガードレールを先に作った

### 本番：失格しないためのガード

本番では、Claude Code に `PreToolUse` フックのガードを作らせ、コマンドを実行する前に内容を検査させました。外部サービスへの保存、ルーターへのログイン、`fsync` の無効化、秘密情報の表示などは止めます。`main` への push や配布は人に確認させ、終了間際は操作そのものを止めました。

失格はしませんでしたが、点数は 27,783 点でした。

### 感想戦：スマホから見守る半自動

感想戦では、Claude Code の Pro プランで、できるだけ自動で進めさせました。PR の作成とマージ、配布、ポータルからの負荷走行（Chrome の拡張機能 Claude in Chrome）まで、AI が人の確認なしで進めます。

人の役割は、外から見守ることでした。

- Claude Code の Remote Control やリモートデスクトップで、スマホから状況を確認する。
- 必要なときに追加の指示を出したり、許可を出したりする。
- AWS へのサインインのように、AI に任せない操作だけを自分で行う。

調査も実装も Claude Code が行い、3日間で約200のコミットを重ねて 363,413 点まで伸ばしましたが、目標の50万点には届きませんでした。

### ガードが強すぎた

振り返ると、守りの決まりが強すぎて、修正が思うように進まなかったところがあります。

- **1回に1つの変更を、走行で確かめる。** 1回に10〜20分かかり、点数も走行ごとに ±5% 揺れるので、小さな改善は見分けられませんでした。
- **変更ごとに Issue に記録する。** 後から原因を追うには役立ちましたが、作業時間の多くを占めました。
- **危なそうな操作は、広めに止める。** 例えば、秘密情報の置き場を読む操作は、調べたいだけでも止まりました。

同じことは、ほかのチームの参加記にも書かれていました。[TAK848 さん](https://zenn.dev/tak848/articles/20261031-isucon2026-writeup)は、守りの決まりが強すぎると AI が保守的になると書いています。感想戦1位の記事の「報告と返事待ちが止まる原因になった」も同じ話です。

また、Pro プランの利用上限に達して、作業が止まる時間もありました。

## 考えたこと

- **ガードは「失格の条件」だけに絞る。** ルール違反は確実に止める必要があります。一方で、それ以外の慎重さ（確認、記録、1つずつの検証）は速さと引き換えです。優勝チームは、規則が禁じていない手は測って決めるよう AI に教えていて、危なそうなら止める私たちのガードとは向きが逆でした。どこまでを AI に任せるかを、事前に決めておくべきでした。
- **人の仕事は、操作から仕組みづくりへ。** 優勝チームでも人は判断をしていましたが、それは当日ではなく、準備の改善ループの中でした。当日に人が速く判断するより、AI が自分で測って判断できる環境を先に作るほうが強い、というのが今回の結果でした。
- **比べる土台を先に作る。** 優勝チームは7問の評価セットと評価の仕組みを作り、構成どうしを同じ条件で比べていました。私たちは1回の走行の点数で良し悪しを決めていて、±5% の揺れに埋もれる改善は見分けられませんでした。
- **足しすぎない。** 優勝チームでも、作り込んだ構成より素に近い構成のほうが強く、当日は最小限だけを足していました。私たちのガードや記録の決まりも、足すほど作業が遅くなりました。
- **見守る道具はそろってきた。** Remote Control や Chrome の拡張機能のおかげで、スマホからでも状況の確認と許可ができました。次は、許可を待たずに進められる範囲を広げ、人は方針と最後の判断に集中したいです。

大会で AI を使うのは、もう特別なことではありません。何を AI に任せ、何を人が決めるか、その設計の力も含めて競うようになってきたと感じました。
