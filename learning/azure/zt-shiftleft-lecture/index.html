01

なぜゼロトラスト？ なぜシフトレフト？

「社内だから安全」が通用しなくなった理由と、守る場所を前に寄せる理由。

1-1

「社内だから安全」はもう通用しない

社員のPCが1台乗っ取られたとき、被害はどこまで広がるか。2つの考え方で比べてみましょう。

    1-2

    ゼロトラストの3原則

    「何も信用しない」ではなく、「毎回確かめてから、必要な分だけ信用する」考え方です。モダナイズ環境の部品は、どれもこの3つのどれかを担っています。

    明示的に検証

    毎回、確かめる

    誰が・どの端末から・何をしようとしているのかを、アクセスのたびに確認する。

    • Easy AuthとEntra IDでのログイン（MFA）
    • APIMでのトークン検証
    • Front Door IDの確認
    最小権限

    必要な分だけ渡す

    権限は、必要な操作だけを、必要な範囲にだけ渡す。

    • Managed IDに「読むだけ」のロール
    • Key Vault単位でのロール割り当て
    • DBユーザーは読み書きのみ
    侵害を前提

    破られても広げない

    どこかが破られる前提で、被害が広がらないよう区切り、見張る。

    • VNetで閉じる・Private Endpoint
    • NSGやネットワークポリシーで区切る
    • 実行中の監視（Defender）
    1-3

    クラウドでも、守るのは自分たち

    責任共有モデル。クラウドに任せられる範囲は使い方で変わりますが、データ・アカウント・端末はどのモデルでも利用者の責任です。列の見出しを押すと説明が出ます。

    1-4

    シフトレフト：見つけるのは早いほどいい

    開発の流れを左から右に並べたとき、問題を見つける場所をできるだけ左（早い段階）に寄せる考え方です。同じ脆弱性でも、どこで見つけたかで後始末が変わります。

    講師メモ
    • 1-1（4分）：境界型で実行 → ゼロトラストに切り替えて実行。「どちらも最初のPCは乗っ取られる」点を強調する
    • 1-2（2分）：3原則は、この後の章で何度も出てくるタグとして紹介するだけでよい
    • 1-3（2分）：「App ServiceはPaaSだから安全」ではなく、ネットワークの設定やIDは自分たちの責任だと伝える。省略可時間が押したら口頭で一言にする
    • 1-4（2分）：「本番」を選んで、やることの多さを見せる。問いかけ「本番で脆弱性が見つかったら、誰が何をする？」
    02

    ネットワークの基本

    モダナイズ環境が「VNetに閉じている」とはどういうことか。一番つまずきやすい名前解決まで。

    12分SC-500 ・ ストレージ・DB・ネットワーク
    2-1

    4つの言葉

    自社専用の敷地

    VNet

    クラウドの中に作る、自分たち専用のネットワーク。外からは見えない。

    敷地の中の区画

    サブネット

    VNetを用途ごとに区切ったもの。APIM用、AKS用、Private Endpoint用など。

    区画の入口の関所

    NSG

    サブネットに出入りする通信を、ルールで許可・拒否する。

    専用の出入口

    Private Endpoint

    Key VaultやDBなどのサービスへの入口を、VNetの中にプライベートIPで作る。

    2-2

    Private Endpointと名前解決

    同じ kv-orders.vault.azure.net でも、どこから・どんな設定で引くかで、返ってくるIPアドレスが変わります。設定を切り替えて確かめてみましょう。

    ← 図は横にスクロールできます →

    2-3

    NSGのルールは、優先度の小さい順に評価される

    AKSのサブネットに付けたNSGの受信ルールの例です。届く通信を選ぶと、上から順に評価して、最初に一致したルールで許可・拒否が決まります。既定のルールでは、VNet内からの通信はすべて許可されている点に注意してください。

    講師メモ
    • 2-1（2分）：敷地のたとえで十分。細かいアドレス設計には入らない
    • 2-2（6分）：「VNet内・PEあり・DNSリンクなし・パブリック無効」で拒否されるのを見せる。運用で一番多い問い合わせなので時間をかける
    • 2-3（4分）：「別サブネットのVMから」を、拒否ルールなし → ありで比べる。省略可時間が押したら「優先度は小さい順」「VNet内は既定で許可」の2点だけ口頭で

        流す脆弱性

        4-2

        脆弱性対応を習慣にする

        ツールは見つけてくれるだけです。直す流れを決まったリズムで回して、初めてシフトレフトになります。

        1. PRが届くDependabotが、更新が必要なライブラリのPRを作る
        2. CIで確かめるテスト、SAST、Trivyが自動で走る
        3. レビューしてマージ放置しない。週に1回など、見る日を決める
        4. 再ビルドコードが変わらなくても、ベースイメージの更新のために定期的に
        5. デプロイACRにプッシュし、App ServiceとAKSへ
        6. 本番を見張る新しい脆弱性や不審な動きを監視し、次のPRへ
        講師メモ
        • 4-1（7分）：「古いライブラリ」「APIキーの直書き」を流す。最後に「本番での不審な動き」を流し、シフトレフトは右側（実行中の監視）を捨てることではないと伝える
        • 「SQLの文字列連結」はSASTを切ると本番のWAFで止まる。03章のA1とつながる
        • 4-2（3分）：チームで実際に回しているリズム（曜日や担当）を一言添える
